> 想象一次取消接口的轻微抖动：搜索 API 完全健康，却被同一个熔断器一起屏蔽；4xx 业务错误（"该日期已满房"）撑爆了为 5xx 熔断设计的失败预算；HTTP 429 限流信号被自动重试淹没，反而拖垮了供应商的容量。这一切都不是因为重试不够多，而是因为重试先于分类发生。

供应商韧性的起点是错误分类，而不是重试策略。

## 为什么重试往往是在帮倒忙

> "重试不是越多越好。重试是分类系统的下游消费者。"

大多数平台遇到供应商失败的第一反应，是加重试：加个指数退避，再配个熔断器——如果团队读过那几篇经典博客的话。但很少有人先问一句：供应商到底在报什么类型的错误？重试是让情况变好，还是更糟？

这个区分之所以关键，是因为不是所有失败都等价，但大多数平台把它们倒进同一个桶里。

- **瞬态基础设施错误** —— 网络超时、连接失败、HTTP 5xx。属于可恢复的网络/进程级抖动，重试合理。
- **限流信号（HTTP 429）** —— 供应商在明确喊"慢点"。立刻重试等于攻击对方容量，会把对方压垮、把已恢复的连接拖坏。
- **业务级 4xx 错误** —— 无效目的地代码、房态已满、价格变动。属于预期内的应用结果，重试只会浪费资源并误导监控指标。
- **凭证或配置失败** —— 凭证过期、密钥被吊销、租户被禁用。属于安全或配置问题，反复重试可能触发账号锁定并留下审计隐患。

没有分类，重试策略就变成一把钝刀：在平台最该卸压的时刻，反而放大负载。监控看到的"失败率上升"其实是分类系统失灵，而不是供应商真的不可用。

## HotelByte 的取舍：先分类，再决策

> "熔断器不是看见失败就跳。它是分类系统对外暴露的执行器。"

HotelByte 的供应商韧性工程层建立在相反的假设上：任何韧性决策之前，必须先完成失败分类。平台把出站失败分为上面四类，并把它们路由到不同的控制路径：

- 业务错误不计入熔断阈值，也不计入限流失败预算。
- 限流响应触发自适应学习引擎（见下一节），而不是盲目重试。
- 凭证失败立即暴露给运维人员，不藏在重试循环里。
- 瞬态基础设施错误才进入标准的重试 + 熔断路径。

熔断器的实现粒度是 `supplier:apiName` 维度，而不是整家供应商。这是一个细微但致命的边界：某供应商的取消接口异常，不应消耗同一家供应商搜索接口的失败预算——后者可能完全健康。维度隔离防止了交叉污染，确保在部分降级时控制仍然精确。

## 限流双引擎 + 录制回放：让控制可以验证

> "韧性控制的失效模式是：你相信它工作，只是因为代码看起来对。"

限流采用双引擎架构。**配置驱动引擎**按凭证维度强制执行静态限速，可全局生效也可按 API 名细分——`byApi` 选项允许对高成本操作（比如取消、预订）单独压低速率。**自适应学习引擎**则响应实时 HTTP 429 信号，从近期请求窗口计算安全阈值（`learnedLimit = count × 0.8`），持久化到分布式缓存。**严格 QPM 调度器**平滑请求准入，避免区间边界的突发-饥饿模式。结果是：供应商侧的配额变化可以被自动吸收，无需人工调参或紧急发布。

录制与回放层提供了让一切可验证的取证能力。**边界检测器**把请求分为边界触发类（HTTP 400+、超时、限流头）和正常流量。边界事件 100% 录制，正常流量按比例采样。**脱敏器**在存储前清除 PII 和凭证。**回放播放器**可以对历史请求在当前实现上重新执行——用于供应商侧变更或平台更新后的回归验证。没有这一层，韧性控制就成了信仰，而不是工程。

## 中间件链：不可绕过的执行顺序

> "顺序不是建议。它由统一执行器强制执行，架构上禁止使用裸 HTTP 客户端。"

中间件链的顺序是刻意且不可绕过的：

```
cache → rate limit → circuit breaker → proxy → HTTP transport → error mapping → cache write
```

每一段都有它的理由，省略任何一段都会放大风险：

- 缓存查询必须排在限流**之前**——重复查询走缓存，不必占用限流配额。
- 限流必须排在熔断器**之前**——避免队列中的请求被熔断器过早拒绝。
- 熔断器必须排在 HTTP 传输**之前**——保护网络与线程资源不被已熔断的供应商消耗。
- 错误映射必须排在响应返回**之后**——把供应商特定的状态码翻译成平台标准结果。
- 缓存写入必须排在最后——只有成功且非空的结果才回写缓存。

这个顺序不是文档里的建议，而是由统一执行器强制实施，且架构上禁止使用裸 HTTP 客户端——任何适配器想绕过中间件链直接发请求，编译期就会失败。

## 什么时候不要这样做

WP07 的取舍是有代价的。它在以下条件**同时**满足时才划算：

1. **多供应商异构** —— 你聚合多个独立的供应商接口，单点重试/熔断无法处理它们的差异。
2. **维度隔离的收益** —— 单个供应商内部存在多个 API，需要隔离失败预算。
3. **运行时同质** —— 团队能维护一套中间件库，统一语言与构建体系。
4. **可观测投入** —— 团队愿意为结构化日志、指标、回放样本付出存储与查询成本。

如果你的供应商单一、调用图浅、或者团队是多语言的，WP07 的中间件框架对你来说反而是负担。HotelByte 这份白皮书的价值，恰恰在于它记录了"反常选择"在什么边界条件下变得理性。
