## 执行摘要

HotelByte 是一个全球酒店 API 分销平台，每天处理数百万个跨搜索、价格、可用性、预订和订单管理领域的请求。在高吞吐量 B2B API 平台中，不受控制的并发性是造成不稳定的主要原因：goroutine 泄漏、不可恢复的恐慌、级联取消和静默任务丢失都会侵蚀企业客户所依赖的服务级别协议 (SLA)。

为了消除这些风险，HotelByte 设计并生产强化了两个互补的并发原语 - `fanout` 和 `errgroup` - 取代了所有业务代码中的原始 goroutine 使用。这些原语强制执行“结构化并发”原则：每个异步任务都有定义的生命周期，每个恐慌都是可恢复和可观察的，并且每个资源绑定都明确受到限制。它们共同构成了并发基础，支持平台的 200 毫秒以下搜索首字节时间 (TTFB) 和 99.99% 的可用性目标。

本白皮书为企业技术评估人员和安全审计人员描述了这些原语的架构原理、操作模型和安全态势。

## 范围

本文档涵盖了 HotelByte 结构化并发层的设计、行为和操作保证，具体来说：

- 用于“即发即忘”操作的 `fanout` 异步任务队列
- 用于结构化并行执行的 `errgroup` 并发任务组
- 两个原语共享的中间件、指标、恢复和背压机制
- 将这些控制措施映射到行业安全和并发标准

超出范围：内部调度可调参数、工作池大小启发式以及特定于部署的基础设施参数。

## 目标

1. **消除非结构化并发**：从业务逻辑中删除所有原始 `goroutine` 使用，将其替换为生命周期、错误传播和资源消耗受到显式限制的原语。
2. **保证优雅的降级**：确保过载条件（通道饱和、内存压力）产生可观察的、可恢复的信号，而不是无声的故障或无限制的 goroutine 增长。
3. **保留任务持久性**：通过可恢复持久性保护非关键路径任务（缓存失效、BI 跟踪、日志报告）免遭进程重启。
4. **启用安全可审计性**：将每个并发控制映射到权威的行业参考（MITRE CWE、OWASP、Go 最佳实践），以便安全审核人员可以跟踪标准的声明。

## 设计原则

### 业务代码中没有原始 Goroutines

不受限制的 goroutine 创建消除了推理资源消耗、故障模式和清理保证的能力。 HotelByte 强制实施硬性架构规则：业务代码必须仅通过 `fanout` 或 `errgroup` 分派工作。这将并发性从临时的实现细节转变为受管理的、可观察的平台功能。

### 负载下的优雅降级

当需求超过容量时，系统必须可预测地降级。当 `fanout` 的缓冲通道饱和时，`fanout` 通过 `ErrFull` 显式暴露背压，让调用者可以选择放弃、重试或升级。 `errgroup` 通过 `GOMAXPROCS` 限制活跃的工作协程，防止并行供应商调用期间出现惊群情况。在这两种情况下，退化都是可测量的，而不是隐藏的。

### 重启后的可恢复性

在部署、节点迁移或内核升级过程中，进程重启是不可避免的。通过 `fanout` 提交的带有可恢复选项的任务会将curl命令序列化到磁盘；重新启动时，原语会通过 `SyncDo` 自动重播它们。这确保了可观测性、缓存一致性和商业智能信号能够在进程短暂终止时幸存下来，而无需人工干预。

### 环境卫生

客户端请求上下文携带适用于同步请求/响应路径的截止日期和取消信号，但对于异步工作来说是致命的。这两个原语都会在异步执行之前分离传入的上下文，从而防止客户端超时中止客户端不再等待的后台任务。

### 默认可观测性

每个并发原语都会发出独立的指标（通道深度、容量、吞吐量、饱和事件），使操作员能够在瓶颈发生之前检测到它们。恐慌会被自动捕获、堆栈跟踪，并使用完整的上下文标签转发到错误跟踪系统。

## 核心架构

HotelByte 的并发层构建在两个互补的原语之上，这些原语解决了分布式系统中并发工作的两种主要模式：**即发即忘异步任务**和**结构化并行执行**。

### fanout — 即发即忘异步任务队列

`fanout` 是一个通道支持的异步任务队列，专为非关键路径操作而设计：缓存失效、BI 事件跟踪、异步日志报告和预订后副作用。它遵循固定的工作池模型，具有以下特征：

- **工作池**：可配置数量的长寿命 goroutine（默认值：1）从共享缓冲通道消耗。无论提交率如何，这都会限制 goroutine 计数。
- **中间件链**：可以注册全局中间件来包装每个 `FanoutHandler`，从而实现指标、日志记录和速率限制等横切关注点，而不会污染业务代码。中间件的嵌套类似于 HTTP 中间件。
- **紧急恢复和报告**：每个任务都在延迟恢复块内执行。如果发生恐慌，则会记录堆栈跟踪并将其连同环境和服务标签一起转发到 Sentry，同时工作 goroutine 继续处理后续任务。
- **上下文分离**：传入的上下文在入队之前与客户端取消信号分离，确保后台工作不会被不耐烦的 HTTP 客户端孤立。
- **反压感知**：当通道饱和时，`Do` 方法返回 `ErrFull`，为调用者提供明确的信号。 `SyncDo`变体使用上下文超时来短暂阻塞，适合不能丢弃的任务。
- **可恢复持久性**：启用可恢复选项后，携带curl命令有效负载的任务将使用唯一的任务ID序列化到磁盘。进程重新启动时，原语会扫描任务目录并通过 `SyncDo` 重播每个项目，然后在成功执行后清理持久文件。
- **独立指标**：`fanout_chan_size`、`fanout_chan_cap`、`fanout_count` 和 `fanout_chan_full_count` 提供对队列深度、容量、吞吐量和饱和频率的按命名扇出可见性。

### errgroup — 增强型并发任务组

`errgroup` 是 `golang.org/x/sync/errgroup` 的增强变体，专为结构化并行执行而设计，其中多个子任务有助于单个逻辑操作（例如，在搜索请求期间并行查询多个酒店供应商）。

- **恐慌恢复和报告**：与 `fanout` 一样，`errgroup` 生成的每个 goroutine 都在延迟恢复块内运行。紧急情况会转换为错误、记录并报告给 Sentry 以及完整的上下文。
- **GOMAXPROCS 并发控制**：`GOMAXPROCS(n)` 方法与 `n` 长寿命 goroutine 建立固定工作通道。当任务超过工作线程容量时，它们会在内部排队，而不是生成无界的 goroutine。
- **错误时取消**：当使用 `WithCancel` 构造时，任何子任务中的第一个非零错误都会触发整个组的上下文取消。当并行供应商调用失败时，这可以防止浪费工作和提前退出相关子任务。
- **确定性等待**：`Wait()` 会阻塞，直到所有子任务完成（或取消）并返回遇到的第一个错误，为调用者提供单个可预测的同步点。

### 互补角色

|图案|原始|保证|典型用例|
|---|---|---|---|
|即发即忘 | `fanout` |有界工人、背压、耐用、无需来电等待 |缓存失效、BI 跟踪、日志报告 |
|结构化并行| `errgroup` |有界并发、错误取消、确定性等待 |并行供应商查询，多步聚合|

这些原语共同涵盖了平台中并发工作的全部范围。业务工程师永远不会在“快速但不安全”和“安全但复杂”之间做出选择；他们选择其保证与业务模式相匹配的原语。

## 操作流程/生命周期

### 扇出生命周期

1. **初始化**：使用 `worker`、`buffer` 和可选的 `resumable` 设置创建名为 `fanout`。如果可恢复，则在接受新工作之前，将扫描任务目录并通过 `SyncDo` 重播挂起的任务。
2. **任务提交**：`Do`立即入队或返回`ErrFull`。 `SyncDo` 会阻塞，直到通道接受任务或调用者的上下文到期。
3. **上下文分离**：任务的上下文与调用者取消分离，然后包装在中间件链中。
4. **执行**：工作线程使任务出队，在紧急恢复下执行它，并发出指标。
5. **清理**：成功后，可恢复任务文件将被删除。在恐慌中，工人幸存下来并报告了错误。
6. **关闭**：`Close()` 向工作线程发送哨兵 nil 项，通过 `sync.WaitGroup` 等待正常耗尽，并取消内部上下文。

### errgroup 生命周期

1. **构造**：`WithContext`创建一个没有cancel-on-error 的组； `WithCancel` 创建一个组，其上下文在第一次错误时被取消。
2. **并发绑定**：可选的`GOMAXPROCS(n)`建立工作通道。如果省略，每个 `Go` 调用都会直接生成一个 goroutine（仍在 `do` 恢复包装器内）。
3. **任务提交**：`Go`提交一个函数。在 `GOMAXPROCS` 下，任务在工作通道或内部切片中排队（如果通道已满）。
4. **执行和恢复**：Workers在`do`内部执行任务，`do`恢复恐慌，将其转换为错误，并向Sentry报告。
5. **错误传播**：第一个错误通过`sync.Once`记录；如果启用了错误取消，则组上下文将被取消。
6. **同步**：`Wait()` 将内部队列排入工作线程，在 `sync.WaitGroup` 上阻塞，关闭工作线程通道，并返回第一个错误。

## 实施的控制摘要

|控制|客户价值 |
|---|---|
| **没有原始 Goroutines** |消除资源泄漏和无法追踪的故障；所有并发都由具有明确生命周期和边界的原语控制。 |
| **基于通道的工作池** |无论负载如何，goroutine 计数都是固定的，从而防止流量高峰期间内存耗尽和调度程序抖动。 |
| **每个任务的紧急恢复** |单个坏任务不会使进程崩溃或杀死工作池；保持服务连续性。 |
| **哨兵集成** |恐慌会被自动跟踪、标记和警报，从而缩短潜在错误的平均检测时间 (MTTD)。 |
| **上下文分离** |后台任务在客户端超时后仍然存在，确保缓存失效和 BI 事件不会被静默丢弃。 |
| **背压信号 (`ErrFull`)** |呼叫者收到明确的饱和信号，从而启用断路器或负载削减策略，而不是隐藏的队列膨胀。 |
| **可恢复持久性** |任务在进程重新启动后仍然存在，不会丢失数据或手动重播，从而提高缓存一致性和分析完整性。 |
| **中间件链** |统一应用横切关注点（指标、身份验证、速率限制），而不会在业务代码中分散逻辑。 |
| **出错时取消** |失败的并行子任务会立即释放资源并取消相关工作，从而防止浪费计算和过时的数据聚合。 |
| **GOMAXPROCS 节流** |并行供应商查询受到限制，保护上游合作伙伴免受过载并保持尾部延迟可预测。 |
| **独立指标** |每个基元、每个名称的指标可实现主动容量规划和快速瓶颈识别。 |
| **结构化关闭** |两种原语都支持使用 `sync.WaitGroup` 进行优雅的排空，确保在滚动部署期间完成正在进行的工作。 |

## 可审计性

HotelByte 的并发原语旨在可由内部安全团队和外部审计员通过以下机制进行验证：

1. **静态代码分析**：存储库通过自动代码审查规则强制执行“无原始 goroutine”规则。在业务代码中引入任何裸露的 `go` 语句都会被标记为阻塞违规。
2. **指标保留**：`fanout_chan_size`、`fanout_chan_cap`、`fanout_count` 和 `fanout_chan_full_count` 导出到 Prometheus 并保留在 Grafana 中，提供队列行为和饱和事件的历史证据。
3. **错误跟踪可追溯性**：`fanout` 或 `errgroup` 恢复的每个恐慌都会转发到 Sentry，并带有完整的堆栈跟踪、时间戳、服务标签和环境标签。审计员可以将恐慌事件与部署时间表关联起来。
4. **可恢复任务审计跟踪**：可恢复任务使用唯一的任务 ID 和curl 有效负载写入磁盘。任务目录充当进程重新启动后幸存的异步工作的持久审核日志。
5. **代码审查规则版本控制**：与并发相关的审查规则 (v2.15) 作为结构化文件存储在存储库中，为构成合规并发使用的内容提供可审核的版本化定义。
6. **回归测试**：两个原语都有专用的单元和示例测试，用于执行恐慌恢复、背压、上下文取消和正常关闭。每次构建都会生成测试报告。
